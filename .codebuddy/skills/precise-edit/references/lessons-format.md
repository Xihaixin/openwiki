# 教训沉淀规范

## 一、两类产物的区分

| 产物 | 存放位置 | 内容性质 | 生命周期 |
|---|---|---|---|
| 长期技术约定 | `.codebuddy/project/LESSONS.md` | 跨任务反复适用的规则、项目特有的坑、必须遵守的联动要求 | 长期保留,定期精简 |
| 任务过程性总结 | `.aidocs/openwiki/<YYYY>/<MM>/` | 单次任务的过程回顾、决策记录、一次性经验 | 归档留存 |

判断标准:该教训在下一次不同任务中是否仍然适用?是 → 长期约定;否 → 过程总结。

## 二、LESSONS.md 条目格式

采用四段式,缺一不可:

```markdown
- [YYYY-MM-DD] 【现象】问题描述,一句话说清出错时的表现
  - 【根因】导致该问题的根本原因,而非表面原因
  - 【正确做法】下次遇到同类场景应采取的具体动作
  - 【触发场景】什么情况下这条规则会被激活
```

示例:

```markdown
- [2026-08-29] 【现象】修改服务层返回结构后,前端收到 500,响应字段缺失
  - 【根因】只改了 core/services 的返回值,未同步 api/models.py 中的响应模型
  - 【正确做法】变更服务层返回结构时,必须同步检查并更新 api/models.py 对应模型
  - 【触发场景】任何涉及 API 响应结构变更的任务
```

## 三、写入流程

1. 提取候选教训:本次任务中用户指出的错误、AI 判断失误、返工点。
2. 逐条判断是否长期有效;否 → 只写入过程总结。
3. 是 → 全文检索 `.codebuddy/project/LESSONS.md`,检查是否已存在同类条目。
   - 已存在 → 合并更新该条目(补充更准确的根因或做法),不新增。
   - 不存在 → 按四段式追加。
4. 追加后检查条目总数;超过 50 条时执行精简。

## 四、防膨胀规则

- 条目上限 50。超限后,将「最近两个季度未被触发场景命中」的条目移入文件末尾的历史区,正文只保留活跃条目。
- 同一根因的不同表现必须合并为一条,不得重复登记。
- 措辞必须可直接执行,禁止「注意」「小心」这类无动作的空泛表述。

## 五、过程性总结格式

文件名:`<主题>-summary.md`,例如 `redis-cache-refactor-summary.md`。

```markdown
# <任务主题> 过程总结

- 日期:YYYY-MM-DD
- 涉及模块:...

## 任务目标

## 关键决策与理由

## 遇到的问题与纠正

## 可复用的经验

## 遗留问题
```

## 六、禁区

`.aidocs/archive/` 由用户手动维护。**AI 严禁对该目录执行任何写入、修改、删除操作。** 复盘流程如需引用归档内容,只读。
